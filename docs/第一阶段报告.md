## 五、完整性约束

第3周建表时已定义主码、外码、部分 UNIQUE（Inventory.product_id、Member.phone、Employee.phone）、DEFAULT、NOT NULL 和部分 CHECK。第4周补充如下约束：

| 约束名 | 类型 | 表 | 说明 |
|---|---|---|---|
| UQ_Product_NameCategory | UNIQUE | Product | 候选码：商品名称 + 类别唯一 |
| UQ_PetService_Name | UNIQUE | PetService | 候选码：服务名称唯一 |
| CK_OrderDetail_Subtotal | CHECK | OrderDetail | 小计 = 数量 × 成交单价 |
| CK_InventoryLog_Sign | CHECK | InventoryLog | 入库为正数、销售为负数 |
| CK_PetService_Duration | CHECK | PetService | 预计时长必须为正数 |

验证用例（脚本 `sql/07_constraint.sql`）：

- 合法数据成功：新增商品、库存、入库记录、订单与明细均成功写入。
- 非法数据被拒绝：重复商品名称+类别、小计与数量×单价不符、入库数量为负、引用不存在的商品、非法支付方式，均被约束拒绝。

截图见 `result/06_完整性约束验证.png`。

## 六、角色与权限

根据第1周角色清单，创建三个数据库角色（脚本 `sql/08_role.sql`）：

| 角色 | 数据库角色 | 主要权限 |
|---|---|---|
| 店长 | role_manager | 商品、库存、服务、员工、订单、会员的查询与管理（SELECT/INSERT/UPDATE/DELETE） |
| 店员 | role_clerk | 接待、销售、办会员、登记预约所需 SELECT/INSERT/UPDATE；不授予 DELETE 和员工表访问 |
| 系统管理员 | role_admin | 通过 db_accessadmin、db_securityadmin 管理用户、角色与权限 |

会员/顾客不直接连接数据库，通过应用系统访问，因此不建立数据库角色。

验证用例：

- 正常操作成功：店员查询商品库存、办理订单；店长查看员工、修改商品价格。
- 越权操作失败：店员查看员工表、删除商品、删除订单均被拒绝（权限不足）。

截图见 `result/07_角色权限验证.png`。

## 七、实验过程

1. 第1周：确定经营场景、角色、业务流程、数据边界。
2. 第2周：设计 9 张表，定义字段、主码、候选码、外码，写样例元组。
3. 第3周：编写建库、建表、插入数据、CRUD 脚本，在 SSMS 中执行成功。
4. 第4周：编写多表查询、统计视图、完整性约束、角色权限脚本，并在 SQL Server 中实际执行验证通过。
5. 第5周：ER 图、规范化、迁移脚本、v0.1 汇总（张文欣负责）。

## 八、实验总结

本阶段围绕宠物店经营场景，完成了从业务分析到可运行数据库原型的完整闭环（v0.1）：

1. 第1周确定经营场景、角色、业务流程与数据边界，明确哪些数据进入数据库、哪些暂不进入。
2. 第2周将业务对象转化为 9 张关系表，定义字段、域、主码、候选码、外码，并说明订单与明细拆分、散客 member_id 可空、库存与库存日志拆分等设计理由。
3. 第3周编写建库、建表、插入样例数据、CRUD 脚本，在 SQL Server 中执行成功。
4. 第4周完成多表连接查询、聚合统计、子查询，封装 5 个统计视图，补充候选码 UNIQUE 与业务 CHECK 约束，并按最小权限原则划分角色、测试越权操作。

从空库按 README 顺序执行 8 个脚本即可完整复现 v0.1，所有脚本均在 SQL Server 中实际执行验证通过。
