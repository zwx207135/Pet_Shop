## 0. 结论摘要

1. v0.1 的 9 个关系中，8 个已经达到 3NF/BCNF；唯一的结构性规范化缺陷在 `OrderDetail`：`subtotal` 作为普通存储列，存在函数依赖 `{quantity, unit_price} → subtotal`，决定因素不是超码、`subtotal` 又不是主属性，因此 `OrderDetail` 不满足 3NF。
2. v1.0 把 `subtotal` 改为 `PERSISTED` 计算列，不再作为独立存储属性参与函数依赖；`OrderDetail` 恢复为 BCNF。
3. `Orders.total_amount = Σ OrderDetail.subtotal` 是**有意的反规范化冗余**，不是函数依赖意义上的 3NF 违反；v1.0 保留该列，用下单事务写入、用 `regression.sql` 每次校验一致性。
4. 迁移是**非破坏性**的：迁移前后 9 张表的行数、5 个视图的查询结果、订单金额全部一致；`regression.sql` 的 9 组检查全部 PASS。
5. 迁移脚本可重复执行：结构检查使用 `COL_LENGTH`、`COLUMNPROPERTY`、`sys.sequences`、`sys.indexes`、`sys.check_constraints` 等元数据判断，不会重复加列/加序列/加索引。

## 1. 分析方法与符号

### 1.1 函数依赖符号

- `X → Y`：属性集 `X` 的每个取值唯一决定属性集 `Y` 的取值；
- **候选码**：能唯一标识元组的最小属性集；
- **主属性**：出现在任一候选码中的属性；
- **非主属性**：不出现在任何候选码中的属性；
- **2NF**：在 1NF 基础上，消除非主属性对候选码的部分依赖；
- **3NF**：对每个非平凡函数依赖 `X → A`，要么 `X` 是超码，要么 `A` 是主属性；
- **BCNF**：对每个非平凡函数依赖 `X → A`，`X` 必须是超码。

### 1.2 分析口径

1. 以 `sql/02_create_tables.sql`、`sql/07_constraint.sql` 定义的**基表**为分析对象；视图不参与规范化判断。
2. **派生列不当作独立存储属性**：v1.0 的 `OrderDetail.subtotal` 是计算列，本文在函数依赖分析中把它排除；v0.1 的 `subtotal` 是普通列，必须纳入分析。
3. **可空 UNIQUE 列不是严格候选码**：关系理论要求候选码非空。`Employee.phone` 可空，只称为“业务候选码/准候选码”；`Product.category` 可空，`(product_name, category)` 在应用层要求 `category` 非空后才成为真候选码。本文在判断时会注明这一差异。
4. 反规范化冗余（如 `Orders.total_amount`）与规范化缺陷分开讨论：前者是性能/快照取舍，后者是函数依赖导致的更新异常。

## 2. v0.1 函数依赖分析

### 2.1 各关系的候选码与函数依赖

| 关系 | 候选码 | 非平凡函数依赖 | 主属性 | 范式判断 |
|---|---|---|---|---|
| `Product` | `product_id`；`(product_name, category)`（应用层要求 `category` 非空） | `product_id → product_name, category, price, stock_warn, status`；`(product_name, category) → product_id, price, stock_warn, status` | `product_id, product_name, category` | 3NF、BCNF |
| `Inventory` | `inventory_id`；`product_id`（UNIQUE） | `inventory_id → product_id, quantity, update_time`；`product_id → inventory_id, quantity, update_time` | `inventory_id, product_id` | 3NF、BCNF |
| `InventoryLog` | `log_id` | `log_id → product_id, change_type, change_qty, change_time, remark` | `log_id` | 3NF、BCNF |
| `Member` | `member_id`；`phone`（NOT NULL UNIQUE） | `member_id → member_name, phone, points, join_date`；`phone → member_id, member_name, points, join_date` | `member_id, phone` | 3NF、BCNF |
| `Employee`（v0.1） | `employee_id`；`phone`（可空，准候选码） | `employee_id → employee_name, role, phone, hire_date`；`phone → employee_id, employee_name, role, hire_date` | `employee_id, phone` | 3NF、BCNF（按已声明的键） |
| `Orders` | `order_id` | `order_id → member_id, employee_id, order_type, order_time, total_amount, pay_method, order_status` | `order_id` | 3NF、BCNF |
| `OrderDetail`（v0.1） | `detail_id`；业务候选码 `(order_id, product_id)`（**未加 UNIQUE**） | `detail_id → order_id, product_id, quantity, unit_price, subtotal`；`(order_id, product_id) → detail_id, quantity, unit_price, subtotal`；`{quantity, unit_price} → subtotal` | `detail_id, order_id, product_id` | **2NF，但不是 3NF/BCNF** |
| `PetService` | `service_id`；`service_name`（UNIQUE） | `service_id → service_name, price, duration_min, status`；`service_name → service_id, price, duration_min, status` | `service_id, service_name` | 3NF、BCNF |
| `ServiceAppointment` | `appointment_id`；业务上可能 `(member_id, service_id, appoint_time)`，未声明 | `appointment_id → member_id, service_id, employee_id, appoint_time, status, remark` | `appointment_id` | 3NF、BCNF（按已声明的键） |

### 2.2 `OrderDetail` 为什么不是 3NF

v0.1 的 `subtotal` 是普通列，并有：

```text
{quantity, unit_price} → subtotal
```

判断：

- `{quantity, unit_price}` 不是超码：不同的 `detail_id` 可以有相同的数量与单价；
- `subtotal` 不是主属性：它不出现在 `detail_id` 或业务候选码 `(order_id, product_id)` 中；
- 因此该非平凡函数依赖违反 3NF 定义；
- 由于 `{quantity, unit_price}` 也不是超码，`OrderDetail` 同时违反 BCNF。

`OrderDetail` 仍满足 2NF：以业务候选码 `(order_id, product_id)` 为键时，`quantity`、`unit_price`、`subtotal` 都依赖完整的 `(order_id, product_id)`，不存在只依赖 `order_id` 或只依赖 `product_id` 的非主属性。

> 即使不把 `(order_id, product_id)` 当作候选码（数据库未加 UNIQUE），`subtotal` 也不是主属性，`{quantity, unit_price}` 仍不是超码，3NF 违反的结论不变；只是“2NF”在单属性主码 `detail_id` 下自动成立。

### 2.3 v0.1 的更新异常

**（1）小计更新异常（主要问题）**

样例 `D001`：`quantity = 1`、`unit_price = 128.00`、`subtotal = 128.00`。

- 若把数量改为 2，却忘记改小计，`CK_OrderDetail_Subtotal` 会拒绝更新；
- 若该约束被临时禁用、或旧脚本绕过约束，则出现 `quantity = 2`、`subtotal = 128.00` 的错误数据；
- `Orders.total_amount` 仍按旧小计汇总，订单金额、商品销售额、会员消费额全部失真。

这不是“应用写得不够仔细”，而是把派生属性当成独立属性存储后必然存在的更新异常。规范化处理是**消除该存储属性**，而不是继续加触发器补丁。

**（2）订单总额漂移（反规范化冗余）**

`Orders.total_amount` 与明细合计语义相同。若直接修改 `OrderDetail.quantity`/`unit_price` 而不更新订单头，订单总额会漂移。它与 `subtotal` 不同：`total_amount` 是跨行聚合，不是 `Orders` 表内的函数依赖，因此不算 3NF 违反；但仍是需要事务保护的冗余。

**（3）类别/角色字符串重复（非范式问题）**

`Product.category`、`Employee.role` 在多个元组中重复。重命名类别（“食品”→“宠物食品”）需要更新多行，漏改会造成分组统计不一致。但：

- `product_id → category`，`category` 不决定其他非主属性，不存在传递依赖；
- `employee_id → role`，`role` 不决定其他非主属性；
- 因此这不是 3NF/BCNF 违反，而是字典表缺失带来的数据质量风险。v1.0 保留文本列，列入 v1.1 改进项。

**（4）不是冗余的属性**

- `Inventory.quantity` 与 `InventoryLog`：前者是当前快照，后者是历史流水；从流水重放可以得到当前量，但成本高且需要完整历史，二者语义不同，均需保留；
- `Member.points`：积分有兑换、人工调整，不能仅由订单金额推导，不是冗余；
- `OrderDetail.unit_price`：是成交价快照，不是当前 `Product.price` 的冗余；商品调价后历史订单必须保持原价。

### 2.4 v0.1 范式判断汇总

| 关系 | 1NF | 2NF | 3NF | BCNF | 说明 |
|---|---|---|---|---|---|
| `Product` | 是 | 是 | 是 | 是 | 两个候选码，所有决定因素为超码 |
| `Inventory` | 是 | 是 | 是 | 是 | `inventory_id`、`product_id` 均为单属性候选码 |
| `InventoryLog` | 是 | 是 | 是 | 是 | 单属性主码 |
| `Member` | 是 | 是 | 是 | 是 | `member_id`、`phone` 均为候选码 |
| `Employee` | 是 | 是 | 是 | 是 | `employee_id`、`phone`；`phone` 可空，严格意义上为准候选码 |
| `Orders` | 是 | 是 | 是 | 是 | 单属性主码；`total_amount` 为聚合冗余，不是 FD 违反 |
| `OrderDetail` | 是 | 是 | **否** | **否** | `{quantity, unit_price} → subtotal`，决定因素非超码、`subtotal` 非主属性 |
| `PetService` | 是 | 是 | 是 | 是 | `service_id`、`service_name` 均为候选码 |
| `ServiceAppointment` | 是 | 是 | 是 | 是 | 单属性主码；业务复合键未声明，不影响当前判断 |

## 3. 分解与保留决策

### 3.1 唯一的结构性调整：`subtotal` 改为计算列

**方案 A：保留 `subtotal` 普通列，加触发器维护**

- 优点：旧代码仍可显式写 `subtotal`；
- 缺点：触发器增加隐藏逻辑；批量更新时性能下降；仍允许直接写入错误值；迁移复杂。

**方案 B：删除 `subtotal` 存储属性，查询时计算**

- 优点：彻底消除冗余；
- 缺点：每次查询订单明细都要计算；按小计排序/索引不方便；旧视图需要改。

**方案 C（采用）：`PERSISTED` 计算列**

```sql
ALTER TABLE dbo.OrderDetail
    ADD subtotal AS CAST(quantity * unit_price AS DECIMAL(10, 2)) PERSISTED;
```

- 数据库自动维护，应用不能写入错误值；
- 物理上仍存储，查询和索引性能与普通列接近；
- `CAST(... AS DECIMAL(10,2))` 与金额列类型一致，避免 `DECIMAL` 乘法结果精度/小数位变化；
- 函数依赖 `{quantity, unit_price} → subtotal` 仍然成立，但 `subtotal` 是派生属性，不再是需要独立维护的基属性，不构成 3NF 违反。

**结论**：v1.0 的 `OrderDetail` 基属性为 `detail_id, order_id, product_id, quantity, unit_price`。

严格按当前数据库约束，`OrderDetail` 只有 `detail_id` 一个已声明候选码；`(order_id, product_id)` 的“同一订单同一商品唯一”目前只是 DAO 的业务约束，数据库尚未加 `UNIQUE`。因此：

```text
detail_id → order_id, product_id, quantity, unit_price
```

这是唯一的非平凡函数依赖，决定因素是超码，达到 BCNF。

如果把 DAO 的业务约束也视为候选码，则还可写出：

```text
(order_id, product_id) → detail_id, quantity, unit_price
```

该决定因素同样是超码，结论不变。两种口径下 v1.0 的 `OrderDetail` 都达到 BCNF；差别只在 v1.1 是否需要补 `UNIQUE(order_id, product_id)`。

### 3.2 没有进一步分解的原因

1. **`Product` 与 `Inventory` 不合并**：二者是 1 : 0..1。合并会让“无库存行”的商品出现 `quantity = NULL`，并把低频的商品目录更新与高频的库存更新放在同一行，增加锁竞争。拆开是正确设计，不是冗余。
2. **不为 `category` 建字典表**：`product_id → category`，没有传递依赖；建表不会提升范式，只会增加连接。当前类别数量少，v1.0 保留文本列，v1.1 再按报表需求决定是否字典化。
3. **不为 `role` 建角色表**：`employee_id → role`，角色只有“店长/店员”两个值；权限边界由数据库角色 `role_clerk`、`role_manager` 控制，不依赖 `Employee.role` 做授权。保留文本列不违反 3NF。
4. **不拆分 `ServiceAppointment`**：当前业务一次预约只对应一个服务，`service_id` 是单值外码。若未来支持“一次预约多个服务”，再增加 `AppointmentDetail`，而不是现在预拆。
5. **不删除 `Orders.total_amount`**：它是订单金额快照，报表和页面频繁读取；删除后每次都要 `SUM(OrderDetail)`。保留为受控冗余，由下单事务写入，`regression.sql` 校验 `total_amount = Σ subtotal`。
6. **无损连接与依赖保持**：本次迁移没有做关系分解，只把派生列改为计算列，因此不存在无损连接或依赖丢失问题；所有原属性仍可直接查询。

### 3.3 反规范化清单

| 冗余 | 类型 | 是否保留 | 一致性保障 |
|---|---|---|---|
| `OrderDetail.subtotal` | 派生属性 | v1.0 改为 PERSISTED 计算列 | 数据库自动计算 |
| `Orders.total_amount` | 跨行聚合快照 | 保留 | 下单事务写入；`regression.sql` 校验 |
| `InventoryLog.remark` 中的订单号 | 审计文本 | 保留 | 仅作文本线索，不作为外码；订单号可读 |
| `Product.category` 文本 | 字典缺失导致的重复 | 保留 | 应用层类别列表；v1.1 可字典化 |
| `Employee.role` 文本 | 字典缺失导致的重复 | 保留 | `CHECK` 限定两个值；权限由数据库角色控制 |

## 4. 迁移方案与执行步骤

### 4.1 迁移原则

1. **非破坏性**：不删库重建，保留 v0.1 全部业务数据；
2. **事务包裹**：结构变更在一个事务中完成，失败自动回滚；
3. **可重复执行**：每一步先查元数据，已存在则跳过；
4. **可回归**：迁移前保存基线，迁移后逐项对比；
5. **权限最小化**：应用账号只授予必要对象权限，登录账号只能读凭据视图。

### 4.2 迁移前准备

```text
1. 确认 v0.1 已按 sql/01~08 建好，样例数据完整；
2. 复制/备份 PetCareDB 为 PetCareDB_v01；
3. 用 scripts/capture_results.py 采集基线到 result/week6_baseline.txt；
4. 以 sysadmin/dbo 身份执行迁移；
5. 迁移后用同一脚本采集 result/week6_after.txt。
```

基线采集内容包括：9 张表行数、`v_order_detail`、`v_product_sales`、`v_inventory_status`、`v_member_consumption`、订单总额与明细合计、`Employee` 列清单。

### 4.3 `migration.sql` 的六个步骤

#### 步骤 1：`Employee` 增加登录字段

```sql
ALTER TABLE dbo.Employee ADD login_name VARCHAR(30) NULL;
ALTER TABLE dbo.Employee ADD password_hash VARCHAR(255) NULL;
ALTER TABLE dbo.Employee ADD is_active BIT NOT NULL
    CONSTRAINT DF_Employee_is_active DEFAULT (1);
```

然后回填样例账号：

- `E001` → `manager` / `Manager@123` 的 scrypt 哈希；
- `E002` → `clerk` / `Clerk@123` 的 scrypt 哈希；
- 其他员工 → 登录名为小写 `employee_id`，密码使用店员样例哈希。

回填后执行：

```sql
ALTER TABLE dbo.Employee ALTER COLUMN login_name VARCHAR(30) NOT NULL;
ALTER TABLE dbo.Employee ALTER COLUMN password_hash VARCHAR(255) NOT NULL;
CREATE UNIQUE INDEX UX_Employee_login_name ON dbo.Employee(login_name);
```

**为什么用动态 SQL**：`login_name`、`password_hash` 是在同一批次中刚加的列，SQL Server 在编译整批时还看不到新列；引用它们的 `UPDATE`、`ALTER COLUMN` 必须放进 `sp_executesql`，否则报“列名无效”。

#### 步骤 2：`OrderDetail.subtotal` 改为 PERSISTED 计算列

顺序：

1. 删除依赖 `subtotal` 的视图 `v_product_sales`、`v_order_detail`；
2. 删除 `subtotal` 的 `DEFAULT` 约束（名称由 SQL Server 自动生成，需要查 `sys.default_constraints`）；
3. 用游标删除所有定义中包含 `subtotal` 的 `CHECK` 约束（包括自动命名的 `subtotal >= 0` 和 `CK_OrderDetail_Subtotal`）；
4. `ALTER TABLE ... DROP COLUMN subtotal`；
5. `ALTER TABLE ... ADD subtotal AS CAST(quantity * unit_price AS DECIMAL(10,2)) PERSISTED`；
6. 重建视图（步骤 3）。

**为什么 DROP 与 ADD 分开批次**：同一批次编译时旧列仍然存在，直接 `DROP` 后 `ADD` 同名计算列会报“列名重复”；脚本用两次 `sp_executesql` 分开执行。

#### 步骤 3：视图重建与新增

- `CREATE OR ALTER VIEW v_order_detail`：订单 + 明细 + 商品 + 员工 + 会员，会员为空显示“散客”；
- `CREATE OR ALTER VIEW v_product_sales`：按商品统计销量、销售额；
- 新增 `v_order_header`：订单头 + 会员姓名 + 员工姓名，供店员订单页使用（店员没有 `Employee` 基表权限）；
- 新增 `v_employee_login`：`employee_id, employee_name, login_name, password_hash, role, is_active`，只授予 `petcare_auth`。

所有 `CHAR` 主码/外码在视图中用 `RTRIM(...)` 去掉尾部空格，避免 Python 侧字符串比较出现 `'P001    '`。

#### 步骤 4：新增 9 个主键序列

```text
SEQ_Product, SEQ_Inventory, SEQ_InventoryLog, SEQ_Member, SEQ_Employee,
SEQ_Order, SEQ_OrderDetail, SEQ_PetService, SEQ_ServiceAppointment
```

统一 `START WITH 1001 INCREMENT BY 1`。DAO 用 `NEXT VALUE FOR dbo.SEQ_*` 生成 `P0001001`、`O00000001001` 等编码；起始值 1001 避开 v0.1 的 `P001`、`O2025010101` 等样例编码。

#### 步骤 5：常用索引

```text
IX_Orders_OrderTime
IX_Orders_MemberID
IX_Orders_EmployeeID
IX_OrderDetail_OrderID
IX_OrderDetail_ProductID
IX_InventoryLog_ProductTime
IX_ServiceAppointment_Time
```

覆盖订单列表按时间排序、按会员/员工筛选、明细按订单/商品连接、库存流水按商品+时间查询、预约按时间查询。

#### 步骤 6：迁移版本记录

```sql
CREATE TABLE dbo.SchemaVersion (
    version VARCHAR(20) PRIMARY KEY,
    applied_at DATETIME2(0) NOT NULL DEFAULT SYSDATETIME(),
    description NVARCHAR(200) NULL
);
INSERT INTO dbo.SchemaVersion(version, description)
VALUES ('v1.0', N'第5-6周：登录字段、计算列 subtotal、视图、序列、索引');
```

### 4.4 `09_app_accounts.sql`：应用受限账户

| 账号 | 用途 | 权限 |
|---|---|---|
| `petcare_auth` | 登录校验 | 只读 `v_employee_login` |
| `petcare_clerk` | 店员业务 | `role_clerk`：商品/库存/订单/会员/服务视图的查询，库存更新，下单所需序列的 `UPDATE` |
| `petcare_manager` | 店长业务 | `role_manager`：更完整的商品/库存/员工/报表权限，序列 `UPDATE` |

原有 `clerk_user`、`manager_user` 是 `WITHOUT LOGIN` 用户，只用于 `EXECUTE AS` 回归测试；应用连接使用三个真实登录账号。

**关键修正**：`NEXT VALUE FOR` 需要对序列对象的 `UPDATE` 权限。v1.0 之前只给角色授予了表和视图权限，受限账号下单时会在生成主键处报 229；`09_app_accounts.sql` 末尾按角色实际使用的序列补充了最小授权。

## 6. 风险、回滚与注意事项

### 6.1 回滚方案

1. `migration.sql` 内部使用 `BEGIN TRANSACTION` + `TRY/CATCH`，任一语句失败会 `ROLLBACK` 并 `THROW`；
2. 迁移前保留 `PetCareDB_v01` 备份；若迁移后需要回退，可删除 `PetCareDB` 并从 `PetCareDB_v01` 还原；
3. `scripts/create_test_db.py` 可从当前 `PetCareDB` 克隆 `PetCareDB_test`，测试失败不会影响主库。

### 6.2 迁移后的写库注意事项

1. **不能再显式写 `subtotal`**：它是计算列，`INSERT`/`UPDATE` 显式赋值会报错；DAO 的 `OrderDAO.create_with_details` 已省略该列，旧脚本/ORM 需要同步修改。
2. **`CHAR` 列有尾部空格**：查询返回的 `product_id`、`order_id` 等要 `RTRIM`；视图已处理，DAO 的 `row_to_dict` 也对字符串做 `rstrip`。
3. **序列权限**：新账号必须显式授予 `UPDATE ON OBJECT::dbo.SEQ_*`，否则 `NEXT VALUE FOR` 报 229。
4. **计算列与 `sqlcmd`**：执行含计算列的脚本加 `-I`，否则可能因 `QUOTED_IDENTIFIER` 设置导致元数据/索引问题。
5. **登录账号权限**：`petcare_auth` 只有 `v_employee_login` 的 `SELECT`；不要把业务表权限授予它，否则违反最小权限原则。

### 6.3 残余风险

| 风险 | 说明 | 后续处理 |
|---|---|---|
| 订单至少一条明细未由数据库强制 | 直接 SQL 可插入只有订单头的行 | v1.1 可用触发器或服务层统一入口 |
| 同订单同商品未加 UNIQUE | DAO 合并，但直接插入可重复 | v1.1 增加 `UNIQUE(order_id, product_id)` |
| 订单总额为冗余 | 直接改明细可能漂移 | 事务 + 回归校验；v1.1 可加触发器 |
| 类别/角色文本重复 | 重命名需批量更新 | v1.1 字典表 |
| 预约时段冲突 | 无唯一约束 | v1.1 应用校验/唯一索引 |
| 登录视图暴露哈希 | auth 账号可读 `password_hash` | 课程环境接受；生产改为独立认证服务 |

## 7. 结论

1. v0.1 的唯一结构性规范化缺陷是 `OrderDetail.subtotal` 作为普通列存储，导致 `{quantity, unit_price} → subtotal` 的 3NF/BCNF 违反和更新异常。
2. v1.0 用 `PERSISTED` 计算列消除该缺陷，`OrderDetail` 达到 BCNF；其余 8 个关系在 v0.1 已达到 3NF/BCNF，迁移未做不必要的分解。
3. `Orders.total_amount`、类别/角色文本是受控冗余或字典缺失，不是范式违反；前者用事务和回归保证一致，后者列入 v1.1。
4. 迁移非破坏、可重复、可回滚；迁移前后行数、视图结果、订单金额完全一致，`regression.sql` 九组检查全部 PASS，DAO 63 项集成测试全部通过。
